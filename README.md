# Snow Forecast

A static website (no build step, no API key) with calibrated 15-day snow forecasts for every
Colorado, Utah and California ski resort, plus Whistler. Purgatory is the default. Installable on iPhone from Safari
(Share → Add to Home Screen).

## Run it locally

```bash
python3 -m http.server 8765
```

Then open http://localhost:8765.

## How it works

- `core.js`: forecast engine. Blends 7 models from [Open-Meteo](https://open-meteo.com/), applies
  calibration, converts snow water to inches with a temperature-based snow ratio, and splits
  each ski day into overnight (4 pm–9 am) and lifts-open (9 am–4 pm) snow.
- `resorts.js`: the mountains, their elevations and the weather stations used for each. Generated by
  `scripts/build-resorts.cjs` from [OpenSkiMap](https://openskimap.org) data plus hand-checked overrides.
- `app.js`, `history.js`, `index.html`, `styles.css`: the page.
- `data/calibration.json`: per-model correction factors and weights, made by
  `node scripts/calibrate.cjs`, which compares archived model forecasts with what NRCS SNOTEL
  stations (US) and Environment Canada (Whistler) measured since Nov 2022.

## Adding a mountain

Add it to `OVERRIDES`/`INCLUDE` in `scripts/build-resorts.cjs` if needed, rerun the script (see its
header), then `node scripts/calibrate.cjs`. Resorts without a SNOTEL station within 25 km borrow the
nearest calibrated resort's corrections (within 80 km), otherwise they run uncorrected.

## Powder alerts

`scripts/alerts.cjs` checks the mountains in `ALERT_RESORTS` (default `purgatory`) and sends a push notification through
[ntfy](https://ntfy.sh) when tomorrow has ≥ 4" by 9 am, any of the next 3 days has ≥ 6",
or the 3-day total is ≥ 12". `.github/workflows/powder-alerts.yml` runs it every evening.

1. Install the free **ntfy** app on your iPhone and subscribe to a long, random topic name
   (anyone who knows the name can read it).
2. In the GitHub repo: Settings → Secrets and variables → Actions → add secret `NTFY_TOPIC`
   with that topic name. Optional variables: `SITE_URL`, `ALERT_RESORTS` (e.g. `purgatory,wolf-creek`),
   and thresholds `OVERNIGHT_IN`, `DAY_IN`, `STORM_IN` can be set as env in the workflow.

### Public alert channels (Alerts page)

Every resort has three public ntfy channels by size, 4"+, 8"+ and 12"+ (names in `alert-topics.js`).
The 🔔 Alerts page lists them with Subscribe and copy buttons. `scripts/channel-alerts.cjs` runs in the
same evening workflow: it reads the published `data/upcoming.json` and posts when a ski day in the next 3
reaches a channel's size. Each powder day gets at most a heads-up (first evening it appears) and a final
call (the evening before). What was sent is kept in the Actions cache (`alert-state.json`), not the repo.
Dry run: `node scripts/channel-alerts.cjs`. ntfy.sh allows ~250 free messages a day per sender; a storm
across every resort can come close.

`.github/workflows/calibrate.yml` recalibrates the 15 stalest resorts every week, so each resort is
refreshed about monthly while staying inside Open-Meteo's free limits.

## iPhone widget

`widget/snow-widget.js` is a [Scriptable](https://scriptable.app) widget. Setup steps and a
copy button are on the site at `widget.html`. It reads `data/summary.json`, which
`scripts/summary.cjs` builds during each deploy for the mountains in `WIDGET_RESORTS` (`.github/workflows/deploy.yml`, every 3 hours).

## Resort snow reports

`scripts/reports.cjs` reads official snow reports (last 24 hours, base, season, terrain open) from resort
websites that allow automated access and writes `data/reports.json` on each deploy. It currently covers
Wolf Creek. Other resorts use their nearest SNOTEL station for measured snow. Sites that block bots
(for example Purgatory's) are not read.

## Webcams

`cams.js` lists each resort's cameras (Brown Rice snapshot stills; tapping opens the live view).
Purgatory and Wolf Creek are set up. To add one, find the camera ids on the resort's webcam page
(`player.brownrice.com/embed/<id>`) and add them there.

## Models

The blend uses HRRR, NBM, ECMWF, GFS, Canadian, ICON and UKMO. ECMWF AIFS and NOAA AIGFS are fetched and
shown for reference (model table, forecast range) but kept out of the blend: in a backtest against SNOTEL
adding them didn't reduce errors. AIGFS is hidden at Whistler (`hideAt` in core.js): too little history to
calibrate, and it runs ~2x wetter than the corrected models there. Retest both after the 2026–27 winter.

## Upcoming Snow

`scripts/upcoming.cjs` runs on each deploy and writes `data/upcoming.json`: a lean 7-day forecast for every
resort (blend models only, 5 variables, about a quarter of the normal API cost) plus snow measured in the
last 48 hours (resort report, else the SNOTEL station, fetched for all stations in one request). It powers
the Upcoming Snow ranking and the "last 48 hrs" badge on favorite cards.

## Passes, drive times, storms, map

- `passes.js`: Epic / Ikon / Indy lineups (2025–26, from memory; update when lineups change).
- Drive times: the viewer taps "Use my location"; the browser's location (rounded to ~1 km, kept on the
  device) goes to the public OSRM router once for times to every resort. Estimates ignore winter closures.
- Storm tracker: groups resorts whose biggest 3-day window (≥ 6") starts within a day of each other.
- Snow map: Leaflet + OpenStreetMap tiles, dots sized and colored by the selected metric.
- Getting there (Mountain tab): Google / Apple Maps directions to the base area, plus road-condition sites
  by state (COtrip and the traction law in CO, UDOT and the Cottonwood Canyons page in UT, Caltrans
  QuickMap in CA, DriveBC). Live road data would need a CDOT or UDOT API key (not built yet).
- Trail map (Mountain tab): the resort's own published trail maps (e.g. James Niehues' paintings), the
  newest winter season in the [skimap.org](https://skimap.org) archive. Resorts with one map per area
  (Vail, Copper, Monarch, …) get thumbnails to switch between them. Duplicate uploads are skipped: only
  one uploader's set per season counts, and a PDF + image copy of the same map counts once. `scripts/trail-maps.cjs` picks it
  (weekly, in calibrate.yml) into `data/trail-maps.json`, using the skimap.org areas OpenSkiMap links
  (`skimapIds` in resorts.js; the best name match wins, so a linked neighbor like Snowbird doesn't
  replace Alta). Images load from skimap.org; tapping opens the full-size original. An "Interactive"
  toggle shows OpenSkiMap's embedded map instead.

## Over-forecast correction

Forecasts of snowy days promise more snow than falls (a backtest of the calibrated blend against SNOTEL
found 10–20% too much at 1–7 days ahead), and far-out days rest on just a few models. `correctForLead` in
`core.js` scales snowy days by a factor for how many days ahead they are, and from day 8 leans toward the
ensemble median. `scripts/verify-forecasts.cjs` runs every morning (`.github/workflows/verify.yml`): it logs
the raw blend at every SNOTEL station 1–15 days ahead (`data/forecast-log/`, 75-day window), scores past logs
against what fell, and writes `data/lead-bias.json`. Each lead's factor blends its measured ratio with the backtest
factor by sample size (the backtest counts as 60 snowy station-days); days 8–15 start from day 7's.
The same job writes `data/forecast-trend.json` (how each station's forecast for every upcoming day changed
across the logs), which drives the trend arrows.

## Daily-list chips and best day

- Trend arrows (↑/↓): how a day's forecast changed vs ~3 days earlier, from `data/forecast-trend.json`.
- Model agreement ("3/5 models"): blend models showing at least 1" (or 40% of the blend) that day.
- Best day to ski: next 7 days scored on snow by first chair, snow quality, wind, cold and the crowd meter,
  with a bonus for a bluebird day (`bestDayHTML` in `app.js`).

## How did we do? and wind holds

- **How did we do?** (Models tab, SNOTEL resorts only): the primary station's last 5 storms (runs of wet days
  with at least 0.3" of water), each with the snow measured (daily snow-depth gains of 1–36") and what the site
  showed 1 and 3 days ahead, plus the average miss. `scripts/verify-forecasts.cjs` writes `data/storm-check.json`
  each morning from the forecast logs. Logged forecasts are water, so they're turned into inches with the storm's
  own measured snow/water ratio (6–25, else 12) and scaled by the current lead-time factor (as `correctForLead`
  does), so the comparison is about how much fell, not density. If SNOTEL is down the file keeps its last version.
- **Wind holds** (Daily tab chip, day details, Summary outlook on windy powder days): the strongest gust in lift
  hours (9 am–4 pm), 40+ mph = "Wind holds possible", 55+ mph = "likely" (upper lifts). Model gusts are for the
  model's smoothed terrain, so this is a risk, not a closure forecast. The best-day score uses the same lift-hour
  gust in its single wind factor.

## Crowds, bluebird / flat light, sharing

- **Crowd meter** (Daily tab chip with 1–3 people, day details): a calendar guess, Quiet / Busy / Packed
  (`crowdOf` in `app.js`). Weekdays are quiet, weekends busy. Holiday weeks (Dec 20–Jan 3, spring break
  Mar 8–28) are busy on weekdays and packed on weekends; holiday weekends (Thanksgiving Thu–Sun, MLK and
  Presidents' Day Sat–Mon) are packed. A 6"+ powder morning bumps it up one level. Whistler uses BC holidays:
  no US Thanksgiving or MLK; Family Day is the 3rd Monday of February, the same weekend as Presidents' Day.
  It is an estimate, not ticket or parking data.
- **Sky** (`skyOf`): average lift-hour cloud cover (9 am–4 pm). Under 30% = Sunny, or Bluebird after 4"+ of
  new snow (previous ski day, or the 24 hours before lifts open); over 80% = Flat light. Days with snow or
  rain during lift hours get nothing extra. The best-day bluebird bonus uses the same function.
- **Share** (button next to the favorite star on a resort page): the phone's share sheet with a line like
  `Purgatory: 9" Wed (6" by 9 am) · next 7 days 16"` and the resort's link (`#<id>`, the bare URL for the
  default resort). Browsers without the Web Share API copy the link and show "Link copied".
